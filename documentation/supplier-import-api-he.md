# טיוטת ממשק ייבוא ספקים

ממשק בפיתוח לשלב המסד; טרם אושר או נפרס. כל הפעולות למנהל פעיל בלבד.

`stage_excel_import(batch)` מקבל אובייקט עם `file_name`, `storage_path`, `content_sha256`,
`url` ו-`published_on` אופציונליים, `registry_id` ו-`registry_version_id` אופציונליים,
או `registry_name` ליצירת מאגר. אם נבחר מאגר ללא גרסה, נוצרת לו גרסה חדשה. `rows` היא
מערך של עד 5,000 עצמים עם `row_number`, `raw` ו-`edited`. הערכים הממופים ב-`edited` הם
מחרוזות: `name`, `entity_kind`, `scheme`, `value`, `field`, `phone`, `email`, `address`,
`contact_person`, `website`. `raw` שומר את הנתונים כפי שנקראו. התוצאה מכילה מזהה אצווה
ומועמדי התאמה, או סימון קובץ חוזר. מועמדים אינם החלטות.

`decide_import_rows(decisions)` מקבל מערך של `row_id`, החלטה (`new`, `link`, `hold` או
`skip`) ו-`edited`. בהחלטת `link` נדרש `target_supplier_id`; בדילוג נדרש `note`.

`apply_import_batch(batch)` מקבל מזהה אצווה ומחזיר ספירות `promoted`, `failed`, `pending`.
שורה שכבר קודמה אינה מטופלת שוב; כל שורה מוכרעת מטופלת בתת-טרנזקציה. שגיאה משאירה
אותה ממתינה. שורה ללא החלטה נשארת ממתינה.

## פערים לפני אישור המימוש

- בדיקות pgTAP ובדיקה מול סביבת Supabase מבודדת טרם הורצו. בדיקות PGlite אינן מחליפות אותן.
- ערך `content_sha256` מחושב כרגע בצד הלקוח; המסד בודק פורמט, קיום קובץ וגודל מדווח,
  אבל אינו קורא את תוכן הקובץ עצמו כדי לאמת שהגיבוב תואם. נדרש פתרון אימות בצד מהימן לפני
  שמסתמכים על הגיבוב כהוכחת זהות הקובץ או על זיהוי כפילויות כערובה מלאה.
- יצירת טיפוסי המסד תדרוש עדכון של `web/src/database.types.ts`, שנמצא בין הקבצים שסומנו
  להימנעות משינוי במסגרת עבודת R14; לכן בדיקת התאמת הטיפוסים אינה עוברת כרגע.
- הנחיות `modern-web-guidance` נמצאו במאגר הרשמי ונקראו. החיפוש בהן יבוצע לפני מימוש
  מסך הייבוא, שטרם נבנה.
